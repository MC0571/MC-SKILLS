# Codex 独立任务聊天的权限继承与启动核验

界面显示“完全访问”、全局配置或来源 Agent 的权限，不证明新聊天获得相同权限。2026-10-19 在 Codex 26.1013.40934 中已观察到：`create_thread` 创建的独立聊天实际为 `workspace-write` / `on-request` / 网络受限；应用的委派创建逻辑在无法继承来源权限时会回落到 `auto`，跨工作目录也可能丢弃来源权限。该版本的创建工具没有权限参数，不能靠 prompt 指定权限。此为已观察的版本行为，不推定所有版本都如此。

1. **先核验，再交付执行。** 创建后的第一条指令只要求报告本轮注入的 sandbox、approval、network、permission profile 与可写目录，不执行产品工作或申请提权。派发者核对当前轮次的实际权限记录（如可读的 `turn_context`）与任务所需工作树、临时目录和网络范围；缺字段记未知，不用旧轮次或界面标签补成已验证。权限足够即可，不把完整访问设为所有任务的前置。
2. **按已授权权限选择创建方式。** 对上述继承故障，需要沿用来源聊天已获授权权限时，可用官方 `fork_thread` 的 `same-directory` 从权限已核实的来源聊天重建。该方式已有成功记录，但仍须执行第 1 步，不保证 Fork 必然继承。明确重设子目标、模型、唯一写入工作树和责任边界；Fork 带入的来源聊天历史、heartbeat 与其他目标不构成新负责人的委托，不允许默认写入来源聊天工作树。
3. **做一次最小实测。** 权限核对通过后，从指定工作目录沿项目正常开发入口，在指定临时目录创建、读回并删除自有临时文件；任务需要网络时做一次必要的只读请求。成功即推进原目标，不反复核验稳定权限，也不让用户逐条批准普通开发命令。
4. **不匹配时定位，不循环提权。** 遇到目录不可写或网络拒绝，先区分执行沙箱与真实磁盘/网络故障。界面与运行记录不一致时报告具体差异，使用受支持的配置或获准重建入口；重建后仍不匹配则停止依赖动作，说明平台限制及一次明确的必要操作，不反复创建聊天或让用户重复选择已经生效于界面的设置。不得改应用二进制、内部数据库或安全策略来绕过审批，不换聊天代执行已拒操作；用户拒绝的一次性请求不等于授权扩大权限。
5. **替换时保持单一负责人。** 确认旧聊天及其自有后台任务已停止、必要工作已保全后，归档被替代聊天并交接写权；在既有工作跟踪系统更新负责人。新聊天权限与实测通过后再报告恢复，区分“任务可继续”与“应用自身缺陷已修复”。

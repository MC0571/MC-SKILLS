# 目标塑形与依赖

现有目标不足以指导下一动作时才补充规划。使用项目已有 Issue、Milestone 或等价权威文档；
不因偏好 GitHub 拒绝有效仓内规划，也不为普通子步骤创建管理对象。
已授权规划写入直接进行；未授权外部写入时准备可审阅草案。

| 内容 | 最低需要 |
|---|---|
| 结果 | 谁能观察到什么变化，为什么需要 |
| 验收 | 成功、失败或不可用时的行为 |
| 范围 | 允许改动与明确排除的责任/权限边界 |
| 依赖 | 下一动作真正需要的条件及证据 |
| 验证 | 实现后的验证方法、命令或产物 |
| 后继 | 本批解锁什么，剩余目标由谁承接 |

已有事实足够时引用即可。父 FR/Milestone 保留整体出口和子项关系，
无需包装成巨大的可执行 Issue。已确认但未完成的目标保留承载。

## 分清开始与完成

开始实施需要明确结果、权限、位置和真实前置依赖；调查可以先行。
失败复现、设计与验证计划支持修复开始，不能要求修复后成功证据先存在。
认证/权限、持久化恢复、迁移、多个副作用或跨入口不变量，
先调查真实调用链并列出覆盖面、顺序和失败处理计划，实现后再验证。
普通局部可逆变更不要求系统矩阵，见 [runtime-and-review-evidence.md](runtime-and-review-evidence.md)。

## 判定 hard 依赖

声称上游阻止开始时，说明真实消费者、最小可观察结果、哪里不能安全开始、
隔离实现/样本为何不足，以及仍需真实上游的集成边界。
缺证据先调查，不把 GitHub 关系直接当技术因果。

基础设施、安全或平台自身有已确认独立价值时可独立交付，否则只覆盖首个真实消费者所需。
安全部分先行，残余依赖只限制对应集成；共享载体释放前不启动冲突 writer。

## 最小草案

```text
结果与价值：
验收：
范围与排除：
真实依赖及证据：
验证方法与成功判据：
后继或延期承载：
需要用户决定的边界（如有）：
```

可用的 write-a-goal 可以辅助起草，增强工具缺失不阻塞已有规划能力。
运行身份、模型、消息游标和工作目录留在执行证据中，不作为产品 Issue 常驻字段。

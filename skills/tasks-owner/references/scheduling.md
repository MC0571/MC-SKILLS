# 执行与委派

默认 `local`：当前 Owner 直接完成工作。先确认是否已有可继续的任务或成果，再决定是否委派。
独立探索、局部实现或必要独立审查能节省关键路径时间时才使用宿主原生子任务。
用户明确要求独立长期任务，且宿主提供所需持久恢复能力时，才使用 App 任务。

## 合理拆分

委派需要目标和返回物明确、上下文可压缩、写入边界独立，Owner 能整合并验证结果。
共享产品出口、写入载体和验证/回滚边界的紧密工作通常留在一个批次。
不为填满并发数制造任务，也不把多个独立出口强塞进一个实现任务。

同一载体只允许一个 writer，包含共享工作树、共同状态文件和会相互覆盖的外部对象。
独立载体可并行；共享仓库名称或目标分支不自动构成写入冲突。
工作树并行仍需检查共同 Git 元数据、生成物或外部状态；最终集成串行处理实际冲突。
模型、资源和并发上限遵循宿主配置及用户要求；上限不是必须填满的指标。

## 依赖

- `hard`：缺少条件不能安全开始此动作，指出真实失败方式和证据。
- `soft`：只影响优先级或信息，允许先执行。
- `convergence`：只阻最终集成、合并或发布。

父子关系、同 milestone、blocked-by 都不能单独证明 hard。
可用只读调查、固定接口样本或隔离实现安全开始的部分先做，上游只阻其必需的集成部分。
任务完成或依赖解除后立即处理已就绪后继；已有活动任务不重复创建。

Unit 的产品出口、不变量、归属与收敛链定位用于跟踪同一承诺，不累计修复额度。
只有目标、验收或归属真变才修改权威事实；换文件、PR、审查者或任务名不改变承诺。
多个 PR 必要时记录集成顺序和最终验收位置；上游变化只使受影响证据失效。

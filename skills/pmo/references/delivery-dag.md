# 交付范围、依赖与总体完成

在塑形范围、协调依赖和归属、解锁后继或判断总体完成时读取。图覆盖用户委任的单一仓库。

## 最少规划事实

目标、验收、依赖和延期项使用 GitHub 或项目已有权威规划载体。PMO 仅索引每个交付单元的范围 locator、Owner locator、短状态、共享写入范围和下一解锁条件；Owner 的实现合同、验证矩阵和日志留在 Owner。

一个交付单元应有可观察结果、验收、允许/排除范围、相关依赖和明确归属。共享写入、验证和收口路径的工作通常由一个 Owner 连续完成；有独立价值、权限/风险边界、归属或回滚需要时再拆分。单一健康路径可以一直由一个 Owner 推进，不为填槽新建任务。

规划覆盖完整已确认目标，实施可以分批。当前可执行范围优先，下一步依赖已稳定时提前塑形；不预建空 Owner、工作树或 Writer。只有缺失事实确实影响安全开始时才先调查，不能要求实现成功证据作为开始实现的前提。

创建或修改 Issue 时使用 `$write-a-goal` 或项目既有模板，并遵守现有写权限。Owner 已负责范围内的细化归 Owner，PMO 只维护无主范围与跨单元边界，避免双写同一事实。

## 依赖按所阻动作分类

| 类型 | 判断 | 处理 |
|---|---|---|
| hard | 缺少具体产物就无法安全开始当前动作 | 满足前保持相关动作等待 |
| soft | 影响顺序、优先级或提供补充信息 | 可开始的范围继续 |
| convergence | 只阻最终集成、验证、合并或发布 | 在对应阶段满足，不阻塞独立实现 |

对有争议的 blocked-by，明确“缺少什么、为什么当前动作不能安全开始”。fixture、已确认合同或隔离载体能支持先行工作时释放那部分，真实集成仍保留后续验证，不能把模拟结果声称为真实验收。

消费者所需上游能力不存在或语义不兼容时，由有归属的 Owner 调查；超出其范围的最窄缺口交 PMO 塑形或重分配。仅更新实现计划不需要用户再次批准；改变产品结果或其他用户保留边界才升级。

依赖环先区分开始与收敛条件，纠正错误归属或切出实际可独立交付的范围。不要用新基础设施、伪造完成或一般谨慎解释环。GitHub 原生关系只有在对应写权限存在时修改，关系修订不附带产品范围或优先级变更。

## 所有剩余结果都要有去向

首次建立范围、重大用户纠偏、完成事件暴露缺口，或恢复时无法确定剩余目标，回读完整委任范围。其余周期只更新受变化影响的 Unit、依赖和 Parent 结果。

共享合同保留七种 gap 分类，作为恢复时的短状态，无需每轮重填全表：

| 分类 | 下一步 |
|---|---|
| `execution_ready` | 开始已授权交付 |
| `admission_pending` | 补齐实际缺少的归属或开始条件 |
| `active_execution` | 由可定位的唯一 Owner 推进 |
| `waiting_external` | 记录不可替代外部条件、责任方、证据和恢复条件 |
| `waiting_user` | 给出确需用户决定的边界、推荐和影响 |
| `replan_or_reownership_pending` | 调查、塑形或恢复责任路径 |
| `closeout_pending` | 补齐尚欠的验收或状态收口 |

`frontier_closure_status=complete` 表示已确认范围内没有未归类遗漏，不表示产品完成。还有 execution/admission/replan/closeout 动作时继续做；只有没有安全可执行动作，且每个剩余结果都在真实执行或有合法等待时才整体等待。

Issue OPEN、`ready=0`、无 Writer、旧 blocked-by 或旧 handoff 都不能证明等待。等待信息只需说明受影响范围、缺少的条件、当前证据、下一责任方及 wake/invalidation；不需要 TTL、sentinel 或代次矩阵。新的相关事实使旧等待失效，更新后继续。

用户保留决定包括产品行为、范围/优先级、重大成本/风险、权限/隐私/数据和不可逆外部结果。普通定位、实现路线、验收内修复和已授权范围恢复由 PMO/Owner 处理。仅账户持有人能执行的机械动作属于外部等待，不包装成产品决策。

## 冲突、后继与完成

同一范围已有活动 Owner 时优先复用；共享写入载体不能同时交给冲突执行者。冲突只暂停相关载体，保留成果并恢复唯一归属。相关代码变更影响另一个 Owner 的集成时通知其在对应收敛动作前同步和验证，无需机械中断其独立工作。

观察到合并、Unit 完成或前置条件解除后：

1. 针对该声明回读验收和目标状态；仓库自然语言可能误触发 Issue close，关闭状态本身不足以证明产品结果。
2. 更新它实际满足的依赖，核对相关 Parent 仍缺什么。
3. 同一活动周期启动安全就绪后继或完成必要塑形；若尚不能开始，留下具体条件和下一责任方。

PMO 不重新运行 Owner 全部测试，但必须核验决定总体完成、依赖释放或实际外部结果的关键证据。Issue 验收和适用仓库检查合并使用；具体验证要求由 Owner 的验证权威规则维护。

Child/PR 数量和 fixture 结果不能关闭 Parent。总体完成需要用户结果对应真实证据，所有已确认验收完成，或用户已明确接受延期并有权威承载。只完成当前批次时保留未完成目标、负责人和下一步；PMO 持续负责，不能在规划或首个合并后退出。

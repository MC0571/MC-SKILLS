# 从产品想法到规格

将产品意图推进为有依据、相互一致、可供开发与验收的定义，并让首次接触项目的人理解其价值、设计取舍和具体行为。采用“先调查与规划问题，再围绕主题深入，最后整合审查”的方法。无需已有代码仓库；角色提示词与共同规范均在本 Skill 内，不要求加载其他 Skill。

## 启动与范围

唯一必需输入是产品想法。目标用户、场景、预期结果、约束、不做的内容、已有材料和保存位置均可从上下文提取，不要求用户先填写完整问卷。

1. 读取当前请求、用户反馈及相关现有文档，区分完整目标、本次范围、已确认暂缓和不做的内容。
2. 用具体用户情境表达当前理解，提出推荐的产品形态与核心旅程，标明假设。只有会实质改变方向、范围、可行性或授权的问题才请求用户决定，每轮优先处理最关键的 1～3 个。
3. 等待答案时继续不依赖它的设计。普通细节在已有授权内处理；未获决定的重大取舍可以比较、提出推荐，但不能写成已确认要求。
4. 新产品从产品定义开始；已有基线直接细化当前功能或处理变更。没有代码不阻止设计，也不构成已验证可行性的证据。
5. 默认只产出设计文档与审查结果。调用本 Skill 不自动授权代码实现、创建远程工作项、发布或对外发送内容；已有明确授权继续有效。

首轮给出当前理解、推荐核心旅程、关键假设或问题，以及下一步；不要只汇报计划便结束，继续完成可独立推进的工作。

## Owner 与按需委派

当前主 Agent 是唯一集成 Owner，负责本次范围、共享定义、跨文档决定、任务分配和交付。产品、架构、Spec 是工作角色，不要求固定岗位或固定 Agent 数量。

- Owner 先建立简短问题地图：每个主题要回答什么、现有依据、依赖的决定、预期产物与完成条件。地图留在会话或既有工作跟踪中，不另建任务台账。
- 紧密依赖的工作串行推进；边界明确、输入稳定、修改范围不重叠的专题可以委派并行。不要让多个 Agent 分别决定同一个概念或共同契约。
- 实质设计交付安排未参与编写的独立 subagent 审查；很小的修订可只审受影响内容及其上下游。先形成可审阅候选，再派审查，不为每页固定配置审查者。
- 使用环境提供的 subagent 工具，遵循当前模型与资源约束，不要求特定供应商、模型或插件。明确禁止子 Agent 再派生；不要为内部子任务创建用户侧聊天。
- 子 Agent 返回范围内的候选产物或修改；Owner 整合共享文档。允许直接写文件时明确互不重叠的路径，上游文档的修改建议交回 Owner。
- 阶段交接前，Owner 回读实际候选，核对范围、新增设计选择、共享对象的身份与单值/多值含义，以及影响下游的假设和待决项；整合成明确版本后再交给依赖它的角色。不能把工作者自报完成的候选自动当作有效基线。普通取舍在已有授权内完成，不新增逐阶段用户审批。
- 用户禁用委派或工具不可用时由 Owner 串行完成，明确审查是自审；不能宣称已完成独立审查。报告具体限制，不以缺少工具阻止其他设计工作。
- 工作者完成后收取结果、核对并结束闲置子 Agent；必要修订完成后再复审受影响部分，不无限循环或凭自报完成交付。

### 统一事实与协作契约

此契约适用于 Owner 和所有工作角色，派发时一并传递：

1. **事实**有可定位的来源；**决定**来自用户或负责人在授权内的选择；**假设**是暂用但未证实的前提；**提案**尚未成为决定。只对影响设计的事项标明类别与依据，不给每句话加标签。
2. 用户决定定义产品意图，外部事实约束可行性；二者冲突时保留双方依据并报告影响。不得虚构调研、用户反馈、性能、技术能力或验证结果。模型间达成一致不构成外部证据。
3. 同一规则在一个权威位置维护，下游引用。材料中的建议、示例和生成草稿不自动成为要求；不要用生成文档之间的互相引用证明事实。
4. 只处理分配范围，沿用共享概念和契约。需要改变上游时返回具体建议、理由和受影响内容，不自行覆盖上游或补造重大产品决定。
5. 关键未知只阻塞依赖它的内容；未决分支可以保留方案草案，但不能被下游当作已选定基线。
6. 不派生子 Agent，不自行扩大外部操作或文件修改权限。按输入快照工作，返回所用版本、产物、依据与待决项、检查结果及影响。

### 派发格式

按任务填入下面的内容，删除不适用项；不要将未替换的占位符发给工作者。只加载本轮所需的角色参考。

```text
角色与具体任务：{{本轮要完成的有界结果}}
本次范围与禁止事项：{{包含、不包含、写入边界、禁止再派生}}
输入快照：{{原始要求及相关文档路径/章节、版本或原文快照}}
已有决定与约束：{{当前有效基线，区分假设}}
产物位置与格式：{{文件或会话中的具体结果}}
完成条件：{{可检查的结果，以及读者需要理解的关键问题}}
统一契约：{{上节契约}}
角色指令：{{相应参考文件的提示词}}
```

输入版本可用项目已有修订号、提交或明确的原文快照，不为此建立版本服务。提供相关上游内容、整体目录和必要的邻接契约，不把全部历史聊天灌给每个工作者。

## 工作阶段与输入输出

| 当前工作 | 输入 | 输出 | 使用参考 |
| --- | --- | --- | --- |
| 产品定义 | 想法、场景、约束、反馈、可得证据 | 用户价值、核心体验、共享概念、范围和需求 | [产品角色](references/product.md) |
| 架构设计 | 当前需求、质量要求、运行与集成约束 | 系统边界、职责、数据流、共同契约、重要取舍 | [架构角色](references/architecture.md) |
| 功能细化 | 相关需求、共享概念、适用架构及邻接契约 | 行为、状态、功能契约、异常与验收场景 | [Spec 角色](references/spec.md) |
| 一致性审查 | 原始要求、来源及同一候选版本的全部相关产物 | 有依据的问题、影响范围、覆盖与未验证项 | [审查角色](references/review.md) |

不要求全部 PRD 完成才开始架构：一个核心流程明确后即可逐层细化，技术约束或功能细节暴露问题时返回对应上游。探索中的内容与已决定基线分开，只有稳定输入的专题适合并行。

对本次要求的全部功能维护覆盖关系，必要时使用稳定需求和场景编号：需求 → 适用设计/功能 Spec → 验收场景。小任务可用章节链接。引用即可，不复制需求正文，不引入专用追踪系统。

默认从核心旅程开始验证设计，但不能以一个示例功能替代用户要求的完整范围；其余部分继续完成，或明确指出仍缺什么及为何尚未完成。

## 内容深度、图示与阅读路径

深度以能否支持理解和决定判断，不设固定字数、章节数、备选方案数或图数量，也不在派发时另加篇幅配额。简单决定直接说明；复杂、易误解或影响多个功能的决定，展开其情境、依据、因果关系、代价和限制。不能用“最简单”“更易维护”等标签代替与本项目约束有关的解释，也不能用重复正文或补造功能增加篇幅。

- **产品分析**应让读者知道当前问题为何值得解决、产品如何优于适用的现有做法，以及哪些价值假设尚待验证。没有研究材料时用标明的场景与对照假设推进，给出能支持或推翻关键假设的观察方式，不伪造结论。
- **架构解释**应把产品约束连到技术选择和用户可观察的后果。对有实质取舍的选择解释适用备选方案、选择理由、承担的代价及何种新证据会促使重审；不要拿违反硬约束的方案作陪衬，也不为尚未需要的能力预建结构。
- **必要图示**用来减少理解关系、边界、状态或时序的负担。文字或表格已足够清楚时不加图；关系复杂时在对应权威文档内用 Mermaid 等可维护形式表达，并由其他文档链接复用。说明图要回答什么问题，名称、边界和分支必须与正文契约一致；不能用图替代精确行为、失败语义或验收。已有渲染或解析工具可用时验证语法及显示；否则明确仅做了结构/语义核对，不声称已渲染。
- **整体阅读路径**放在既有产品入口（通常是 PRD）中：用简短全景说明产品、核心旅程和文档分工，提供真实链接，说明理解产品、做技术决策或实现功能分别应读什么。每份专题开头说明本页解决的问题、范围和所需上游，结尾仅在有意义时指向下一步。没有必要不新建目录页，也不把目录复制到所有文件。Owner 最终整合时清理已完成的待生成提示与角色交接过程，只保留仍影响读者的待决项和验证限制。

解释与契约各有用途：解释帮助理解决定，契约精确定义结果，两者在同一权威位置维护并互相支持。引用来源能支持事实，不自动证明设计选择正确；讲解更充分也不等于技术或市场已验证。Owner 在交接与整合时检查上述问题是否得到实际回答，内容已足够支持本次决定后收口，不为追求“全面”无限延展。

## 保存与单一权威来源

优先沿用项目既有文档结构和格式。没有代码仓库也可保存文档，不需要初始化代码项目。无合适工作目录或保存位置不明确时，仅澄清落盘位置，同时在对话中继续起草；不得把产品文档写进 Skill 自身目录。

没有既有结构时，可按内容需要使用：

```text
brief.md          原始意图、硬约束和来源入口（必要时）
prd.md            产品定义、共享概念、范围和需求
architecture.md   跨功能职责、共同契约和重要设计取舍
specs/<功能>.md   具体行为、功能专属契约和验收场景
```

文件数量按规模调整：简单产品可以合并，复杂功能可以拆分。PRD 不承担开发排期；架构不复制功能行为；同一功能不再复制成两套产品/技术 Spec。已有 ADR、原型和研究材料通过链接复用；只有需要时才新增。

来源应能定位到用户原话、文档章节、外部资料或实际观察。每份派生产物标明适用范围与上游版本；关键待决项就近记录其影响。动态任务进度与审查过程留在会话或既有跟踪系统，不强制生成审查报告、变更台账或目录索引文件。

## 需求变更与审查闭环

1. 对照原始要求判断本轮改变的是意图、事实、假设还是设计选择，更新对应权威位置。
2. 沿实际引用和语义关系识别影响范围，包括没有显式链接的概念、权限、状态和数据规则。不要只依赖链接或只审改动段落。
3. 明确标识受影响且未修订的内容不再适用，更新相应架构、Spec 和验收场景，保留无关改动。不整套重写，也不让旧版本审查结论替新版本背书。
4. 审查者直接读取原始输入、当前候选及有关来源，不能只看作者总结。Owner 根据依据裁决发现，修正后补审修改及其对完整当前范围的影响。
5. 如果剩余问题需要用户决定或外部证据，报告具体问题、影响、推荐与验证办法，继续完成其他范围。没有新信息时停止反复生成，不用格式完整掩盖缺口。

## 交付与就绪判断

最终从产品入口给出阅读路径，并交付链接或正文、覆盖的实际范围、关键决定与假设、审查结果和未解决事项。质量判断同时检查解释是否帮助理解、图文是否一致，以及原有契约与验收是否完整，不能仅按篇幅、图数量或文件生成成功判定。用以下含义区分状态：

- **草案可讨论**：方案具体，用户可判断方向，假设与缺口可见。可以没有代码或市场验证。
- **规格可进入开发**：本次范围的关键行为、职责和契约明确；必要技术前提有依据，剩余假设的风险已在授权内接受；阻断冲突已解决，验收可执行。说明是否经过独立审查。规格就绪不等于获得实施授权。
- **实现已验证**：仅在确有实现及适用验证证据时使用；本 Skill 只生成设计文档时不能达到这一状态，也不能把设计审查称为市场需求已验证。

用户只要求某一阶段时，按该阶段交付，不强制完成全套。用户要求完整流程时，持续推进到本次范围完成或明确的依赖阻塞，不以文件已生成、工具成功或单一专题完成代替目标完成。

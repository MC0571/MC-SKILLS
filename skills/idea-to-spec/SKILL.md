# 从产品想法到规格

以故事贯穿产品意图、设计取舍、具体行为与验收，使首次接触项目的人能理解并继续工作。本 Skill 自含角色指导，不依赖其他 Skill，也不要求已有代码仓库。

## 启动与范围

唯一必需输入是产品想法；从当前请求、反馈和已有材料提取目标、范围、约束与来源。
模糊想法先进入产品探索：首轮给出问题理解、候选形态、具体旅程和影响方向的问题，标明假设；不直接扩写整套规格，也不只抛问卷。普通细节在授权内处理，每轮优先澄清最关键的 1～3 项决定，继续不依赖答案的工作。
已有稳定基线直接进入本轮所需工作；只要求探讨时停留在探讨范围。默认交付设计，任务已要求实现或测试时沿用授权继续，不重复逐阶段审批；调用 Skill 不扩大远程工作项、部署、发布或对外发送权限。
沿用项目文档结构与格式；保存位置不明确时只澄清落盘位置，同时继续起草。无代码不阻止设计，不为保存文档初始化代码项目，也不把产品产物写进 Skill 目录。

## 共同契约

- 当前主 Agent 是唯一集成 Owner，亲自负责用户沟通、问题澄清、重要取舍确认与方向收敛。角色是工作职责，不代表必须派发；仅按需要委派有界内部任务。区分完整目标、本次范围、已确认暂缓与不做的内容；完成本次全部要求，核心示例不能替代完整范围。
- 区分有来源的事实、授权内的决定、未证实的假设与未采纳的提案；不虚构研究、能力或验证。模型共识及生成文档互引不构成外部证据；意图与外部约束冲突时保留双方依据并报告影响。
- 同一规则只维护一处权威来源，下游引用。派生产物标明适用范围和上游版本。各角色沿用共享概念和有效版本，改变上游的建议交回 Owner；未决候选不能冒充稳定基线。
- 故事保留动机、上下文、关键步骤与分支，并关联状态/契约、验收及本轮适用的实现。产品拥有体验与故事决定，架构拥有跨功能契约，Spec 拥有局部行为，实施负责代码与执行证据。
- Owner 在阶段交接前回读实际候选，核对范围、设计选择、对象身份与单值/多值、假设及待决项，再采纳为明确版本；工作者自报完成不等于基线有效。

## 推进门槛

当前专题进入规格细化前，须已明确用户任务、成功结果、范围与具体核心体验；关键行为、概念及重要取舍已有决定和理由，会推翻行为的技术前提有依据。需要用户决定的事项须有答复，普通选择在既有授权内完成。
未知只阻塞依赖部分。探索期可提前做可行性核查，候选技术方案不能冒充已选架构；不要求整份 PRD 或整个产品一次定稿。下游暴露新问题时返回受影响决定，不以文档齐备代替收敛。

## 按需读取

进入当前工作前读取对应参考；只加载本轮正在承担的角色或机制，不按表顺序全读。切换工作时再补读。派发时由 Owner 提供短共同契约、适用门槛、输入版本及必要上游内容，工作者只读被分配的角色参考。

| 当前需要 | 读取参考 | 负责内容 |
| --- | --- | --- |
| 探索、收敛或修订产品体验 | [产品](references/product.md) | 故事、PRD、范围与产品入口 |
| 核查技术前提或定义共同契约 | [架构](references/architecture.md) | 职责、跨功能状态、数据与取舍 |

| 已授权实现、测试或同步代码 | [实施](references/implementation.md) | 故事关联的代码及真实验证 |
| 实质候选交付或修订后补审 | [审查](references/review.md) | 独立核对、就绪与交付详细检查 |

角色间传递有关产物和契约，不以读取另一角色全文为前提。功能内部问题不机械升级为全套流程。

## 审查与交付

实质设计或实施候选交付前，由未参与编写的审查者核对当前版本；小修订只审受影响部分及上下游。用户禁用委派或工具不可用时串行完成并如实标明自审，不宣称独立审查。
从现有产品入口提供实际产物链接或正文，说明范围、关键决定与假设、当前版本、验证结果及剩余限制；清理已结束的待生成和角色交接提示。
区分状态：**草案可讨论**是方案具体、假设可见；**规格可进入开发**是当前范围通过推进门槛、阻断冲突解决且验收可执行，不代表实施授权；**实现已验证**须有对应版本的实现及真实执行证据。文档生成、步骤绑定、dry-run、设计审查或角色推演不能替代实现验证或市场验证。
只要求某阶段时按该阶段交付；完整流程持续到本次范围完成或具体依赖阻塞。需要用户决定或外部证据时报告影响与推荐，完成不受阻部分；无新信息时停止重复生成。

# 有效基线与跨产物变更

Owner 在故事、共享概念、接口、前提或决定的变化影响有效基线及其他产物时加载，包括技术核查或本轮技术方案（Plan）反馈推翻产品假设、功能 Spec 暴露共同契约缺口、实施任务（Tasks）发现依赖或落点缺口等情形，不限于用户明确说“改需求”。没有跨产物影响的局部修改直接处理，不强制加载本文件。

沿用主文件的短共享契约、推进门槛和角色归属。以下五步处理本轮受影响范围，不另设所有任务通用流程、变更台账或逐阶段审批。

## 五步闭环

1. **识别变化并更新权威来源**
   对照原始要求和当前有效基线，判断变化属于产品意图、外部事实、假设还是技术选择，说明来源、理由及适用范围。用户决定定义产品意图，外部事实约束可行性。冲突时保留双方依据，提出影响与推荐。涉及用户承诺时，由 Owner 推进产品取舍并更新对应 PRD 或功能 Spec。按主入口的职责定位权威来源，下游引用。

2. **沿语义关系识别影响**
   同时检查显式引用和未链接的关联含义。沿故事动机、步骤、Persona 约束、分支和可见响应，追到适用的业务规则、验收、Plan、架构契约、任务依赖和执行证据。技术选择改变时核对是否影响用户承诺。保留原始叙事与来源，复用既有故事、步骤和场景编号。

3. **标明失效内容并在授权范围内同步**
   标明尚未修订的旧内容在哪些范围失效。更新权威定义及受影响的 PRD、功能 Spec、Plan、架构契约和故事关联，已有 Tasks 同步更新落点、依赖与验证。向工作者提供当前版本和变化，审查或运行证据仅在仍适用的范围复用。

   规划或任务交接沿用本轮授权。已有按故事实施、同步代码或补齐自动化验收的授权时，由 Owner 协调更新受影响的调用方、实现、测试和必要配置，并执行相关验证和回归。写入边界外的修改交回对应负责人，注明未落实的部分。

   已有 `.feature` 承担某项验收时继续以它为权威定义，功能 Spec 与 Tasks 引用它，实际步骤与断言兑现它；不复制同义验收或另建测试栈。故事或 Persona 分支变化须落实到适用前提、动作和断言，不能只改描述。

4. **裁决发现并补审当前候选**
   有需要审查的候选时才读取 [review.md](review.md)。审查者直接读取原始输入、当前候选和有关来源。本轮包含实施时一并核对当前代码、测试与执行证据。Owner 按依据裁决，修订后补审新增修改及其对当前范围的影响，补齐受影响检查。按主入口要求区分独立审查与自审。

   实现或测试失败时先定位实现、测试和环境原因；产品意图与技术能力冲突时回到相应决定。工具成功或失败均不反向放宽用户意图，不通过删减故事、跳过场景或放松断言制造通过。裁决改变基线后重新关联并验证受影响内容。

5. **局部阻塞并如实收口**
   剩余问题需要用户决定或外部证据时，报告具体问题、影响、推荐与最小验证办法，继续完成不依赖它的范围。未决分支可保留候选，不能被下游当作已选基线；没有新信息时停止重复生成，不用格式完整掩盖缺口。

   交付指出当前有效版本、实际同步范围、审查结果、按主入口判断的就绪状态、阻断和未执行项。包含实施时分别报告场景已定义、执行步骤已绑定、真实运行通过/失败及未执行原因，并绑定所用故事、设计、任务、代码、测试版本与环境。实现验证以真实执行证据为依据。按受影响故事验证实际入口及适用的保存、返回与冷重开恢复。

各角色由 Owner 传入短共享契约、必要输入和本轮职责，无需为处理变更读取主文件全文。只有实际委派时才按主入口路由加载协作参考，变更与协作不互设必读。

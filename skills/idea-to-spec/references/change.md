# 有效基线与跨产物变更

Owner 在故事、共享概念、接口、前提或决定的变化影响有效基线及其他产物时加载，包括首次设计中架构反馈推翻产品假设、Spec 暴露共同契约缺口等情形，不限于用户明确说“改需求”。没有跨产物影响的局部修改直接处理，不强制加载本文件。

沿用主文件的短共享契约、推进门槛和角色归属。以下五步处理本轮受影响范围，不另设所有任务通用流程、变更台账或逐阶段审批。

## 五步闭环

1. **识别变化并更新权威来源**
   对照原始要求和当前有效基线，判断变化属于产品意图、外部事实、假设还是设计选择，说明来源、理由及适用范围。用户决定定义产品意图，外部事实约束可行性；冲突时保留双方依据，提出影响与推荐，不把技术限制或实现现状自动改写成需求。按主文件角色归属在单一权威位置维护规则，下游引用；建议和草稿不自动成为决定。

2. **沿语义关系识别影响**
   同时检查显式引用和未链接的关联含义：故事动机与步骤、Persona 约束、分支、共享概念与对象身份、权限、状态及合法转换、数据所有权、组件职责、接口和验收。沿用户动作、可见响应、状态转换、负责模块及适用接口追到下游，不只搜索同名词或检查改动段落。保留原始叙事与来源，复用既有故事、步骤和场景编号，不为此新增追踪系统。

3. **标明失效内容并在授权范围内同步**
   明确标识受影响且未修订的旧内容不再适用，防止后续角色继续当作有效输入；修订其权威定义及相关 PRD、架构、Spec、故事关联和验收场景，保留无关改动，不整套重写。采用新输入的工作者须获得当前版本与变化，旧版本审查或运行结果只在仍适用的范围内复用。

   仅设计任务只同步设计。已有按故事实施、同步代码或补齐自动化验收的授权时，Owner 协调负责角色继续更新受影响的调用方、实现、测试和必要配置，并实际执行相关验证及所需回归。写入边界外的修改交回对应负责人，未落实的部分如实标明，不能仅返回建议便称同步完成。既有授权继续有效，不重复审批，也不扩大到部署、发布或其他外部操作。

   已有 `.feature` 承担某项验收时继续以它为权威定义，设计引用它，实际步骤与断言兑现它；不复制同义验收或另建测试栈。故事或 Persona 分支变化须落实到适用前提、动作和断言，不能只改描述。

4. **裁决发现并补审当前候选**
   有需要审查的候选时才读取 [review.md](review.md)。审查者直接读取原始输入、当前候选和有关来源；本轮包含实施时一并核对当前代码、测试与执行证据。Owner 按依据裁决，修订后补审新增修改及其对完整当前范围的影响，补齐受影响检查，不让旧文或旧审查结论替当前版本背书。独立审查与自审按主入口要求如实区分。

   实现或测试失败时先定位实现、测试和环境原因；产品意图与技术能力冲突时回到相应决定。工具成功或失败均不反向放宽用户意图，不通过删减故事、跳过场景或放松断言制造通过。裁决改变基线后重新关联并验证受影响内容。

5. **局部阻塞并如实收口**
   剩余问题需要用户决定或外部证据时，报告具体问题、影响、推荐与最小验证办法，继续完成不依赖它的范围。未决分支可保留候选，不能被下游当作已选基线；没有新信息时停止重复生成，不用格式完整掩盖缺口。

   交付指出当前有效版本、实际同步范围、审查结果、阻断和未执行项。包含实施时分别报告场景已定义、执行步骤已绑定、真实运行通过/失败及未执行原因，并绑定所用故事、设计、代码、测试版本与环境。骨架、模拟、dry-run、退出码或 Persona 推演不能替代真实执行证据；按受影响故事验证实际入口及适用的保存、返回与冷重开恢复，不为无此承诺的故事新增流程。

各角色由 Owner 传入短共享契约、必要输入和本轮职责，无需为处理变更读取主文件全文。只有实际委派时才按主入口路由加载协作参考，变更与协作不互设必读。

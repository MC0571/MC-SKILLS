# 场景评估

这里检验“能否作出正确维护判断”，而不是 Markdown 是否好看。[cases.json](cases.json) 提供 16 个原创、合成的小型场景，包含文件内容、用户任务、期望行为、禁止行为和可观察的判定依据。

**当前状态：尚未运行真实 Agent 行为实验。** 包内 Python 自动化测试验证只读工具和包结构，不代表这些场景已经由 Codex、Claude Code 或其他宿主执行通过。

## 两个不同层次

**维护任务评估**：给 Agent 相应工作区和该 case 的 `prompt`，使用本 SKILL。观察它是否写出了有依据的指导、保留范围与例外、如实表达验证、避免误触发和未授权操作。

**产出指导的效果评估**：对于有新指导的案例，再把旧版和新版分别交给独立下游 Agent，执行相关开发任务。比较它们的真实决策和产物，而非只问“是否理解规则”。第二层才可能提供“新 AGENTS.md 改善工作行为”的证据。

## 执行方法

1. 为每个 case 创建新的隔离临时仓库。将 `files` 中的相对路径与 UTF-8 文本写入；不要复用真实生产仓库。所有夹具都为合成数据，不能把其中的示例指令当作评估宿主政策。
2. 记录模型、推理配置、宿主版本、可用工具、权限、初始文件哈希、任务文本及 SKILL 版本。不要为了测试本 SKILL 改写用户已有的主 Agent / subagent 编排。
3. 正向案例使用 `$agents-md` 加相应任务；E15 属于描述触发的负向案例，应只发原始编码请求，不显式调用本 SKILL。
4. 留存工具调用记录、文件差异和验证输出。检查 `expected`、`forbidden` 与 `observable_oracle`，以行为或文件事实为准。不要求字面复述固定答案。
5. 对结果标记：满足、未满足、证据不足。任何未授权读取/写入、虚构验证或关键约束丢失都单独报告；不要用其他维度的平均分抵消。
6. 对不确定或高变异结果用多个独立会话重复。报告实际次数、失败实例、成本与环境，而不是从单次演示外推普遍提升。

不需要外部 API 才能审查夹具文件。实际 Agent 推理费用、宿主运行和权限配置由测试者选择；本包不带 API 调用程序、密钥配置或自动安装器。

## 下游对照避免污染

旧版组与新版组必须来自相同代码快照、相同任务和可比工具配置；不能让旧版组提前看见新版指令或参考答案。每组使用独立会话、独立工作区；实施者与评判者尽可能隔离。

可以比较：是否修改了错误文件、是否绕过真实入口、是否误删 Notebook 输出、是否丢失例外、是否伪称测试成功、是否因过度约束阻碍合法方案。成功标准应在运行前写好。

## 如何更新场景

真实使用中出现新失误，先保留可公开的最小复现与正确政策来源，再添加回归案例。不要保存凭据、个人路径或私有代码；不要把一个项目的工程偏好伪装成所有项目的标准答案。

修改 SKILL 时优先重跑受影响场景。为少写几行而降低规则强度、去掉必要例外或绕过验证，不应被评估认作优化。

# 规则设计：从观察到判断

## 先判断信息是否能改变工作

保留能改变关键选择、阻止常见误判、避免高成本重复探索、明确必要权限或说明实际入口的信息。不要把“项目独有”作为唯一标准：明确的选择顺序、团队偏好与安全边界也可能很有价值。

泛化语句只有在能解决明确问题时才保留；例如“优先复用”若有可执行的选择顺序，比一句口号更有用。反过来，一段充满项目路径的目录摘要也可能没有决策价值。

## 候选规则的工作形态

起草时在心里回答：情境是什么、容易选错什么、应该怎样做、原因/例外是什么、如何知道已经满足。最终表达不必强迫五项分别成段。

| 适用内容 | 优先形态 |
|---|---|
| 简单但非默认的操作入口 | 准确命令 + 工作目录 + 必要前置条件 |
| 生命周期、状态和归属 | 边界 + 禁止绕行方式 + 可观察结果 |
| 容易过度工程化的选择 | 有序决策步骤 + 不可牺牲的底线 |
| API/生成源/多构建联动 | 触发变化 + 同步对象 + 生成/验证入口 |
| 复杂领域或低频操作 | 短规则/条件导航 + 深层知识位置 |
| 因惯性反复选错的写法 | 一个正反例 + 必要理由，不写语言教程 |

## 正反例：均为合成示例，不是任何目标仓库事实

### 状态归属

弱：遵循架构，确保会话恢复正常。

强：若当前契约确认会话状态由统一存储持有，提供方适配器不得创建另一个会话状态源。修改切换流程时验证建立会话、切换、恢复操作；仅适配器单测不能替代该路径。

落地前必须把“若当前契约确认”变成已核实的事实，或者只作为待确认建议。不能原样把假设写入正式文件。

### 验证范围

弱：提交前运行所有测试。

强：维护指定 Notebook 时分别检查格式、结构和自上而下执行；实际调用外部 API 的执行入口受环境与授权限制。格式检查成功不能当作 Notebook 已执行。

目标仓库的命令要从其工具中核实，不可复制示例命令。

### 取舍顺序

弱：保持简单，避免过度设计。

强：先确认需求和调用路径，再寻找现有实现、标准能力与已安装依赖；新增抽象必须解决本次可证明的复杂性。最短差异不得牺牲错误处理、边界验证和相关回归覆盖。

这是可选表达思路，不是默认施加给所有仓库的政策。

## 保留、迁移或删除

- **保留**：仍有效，能改变选择或降低探索成本。
- **改写**：重要但含糊，缺少对象、范围、例外或完成标准。
- **合并**：同一对象、同一作用域、同一含义的重复；强度或例外不同先处理歧义。
- **迁移**：低频细节或局部知识有更合适的现有载体；同时保留可达入口。
- **删除**：已失效、重复且另有可靠入口，或无实际作用。不能因可从代码推断就自动删除。
- **待核实**：设计意图、当前版本或冲突证据尚不能确定。

每项重大删改都检查：禁止事项是否弱化，适用范围是否扩大，合法例外是否消失，阅读入口是否断开，验证责任是否丢失。不要求为每个措辞变化生成审计表。

## 不能照搬样本的结论

一个仓库可能用真实服务发现集成问题，另一个需要稳定、无凭据的核心回归。两者可以并存于不同测试层。不要把“真实 vs 模拟”变成无条件道德判断。

同理，依赖优先或少依赖、预稳定 API 或兼容承诺、保留演示输出或清除敏感输出、精确类型断言或运行时校验，都需要目标项目的依据。

不把来源自称最快、最好或最便宜的产品推荐改写为已验证性能事实。用户明确选择的模型名不因知识过期被擅自“纠正”；确需更新外部版本时查当前官方资料。

## 规则强度

必须/禁止用于已确认的义务；优先/通常表达权衡；待确认表达证据缺口。把这些强度互相替换就是改变政策，不只是润色。

存在规则冲突时先核对对象、受众、入口、环境、时期与优先级。不同 Python 示例版本不必然冲突；本地与 CI 使用不同验证层不必然冲突；同一条件下互斥的义务才是真正冲突。

## 根文件不是越短越好

根文件长度由相关性、阅读方式和维护成本决定。全局正确性依赖的规则即使较长，也不能为了行数指标藏进没有触发说明的链接。文件过长时先减少重复、陈旧细节和无关受众，而不是等比例压缩每个章节。

## 输出风格

用具体主体与动作，保持项目既有术语。避免把“提升质量、保证健壮性、遵守最佳实践”当成完成的规则。默认中文，不翻译命令和技术标识。没有证据的路径、测试名、门槛和责任人不得写入正式产物。
